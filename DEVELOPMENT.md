# Development

## Layout

```
projects/label-catalog/   custom app — the catalogue page (TypeScript + React, built with spicetify-creator)
projects/label-link/      extension — the header link, plus a few CSS repairs and the hash capture
scripts/                  dev tooling: sandbox launcher, CDP bridge, live checks, icon generator
```

## Everyday loop

```bash
npm run deploy            # build the custom app + spicetify apply -n
npm run stop && npm start # restart the client to pick the change up
```

The `-n` flag on `spicetify apply` matters: without it Spicetify restarts Spotify
through LaunchServices, which can resolve to the wrong install (see below).

Also available: `npm run watch`, `npm run typecheck`, `npm test`.

## Tests

```bash
npm test
```

Unit tests (Vitest) cover everything that runs without a Spotify client: label
normalisation, filters and sorting, duration/type formatting, and — most
importantly — `buildCatalogue` against a mocked backend. That last suite encodes
the project's core correctness rules: impostor labels are rejected and counted,
paging stops at the backend's reported total instead of walking into
relevance-ranked noise, artist-discography expansion reaches releases the search
never returned, no release is fetched twice, and cancellation actually stops the
work.

Live behaviour is verified against a running client over the Chrome DevTools
Protocol:

```bash
DEBUG_PORT=9222 npm start
node scripts/cdp-eval.mjs scripts/checks/smoke.js          # release → label link → catalogue
node scripts/cdp-eval.mjs scripts/checks/active-release.js # sticky header names the release under it
node scripts/cdp-eval.mjs scripts/checks/capture-error.js  # captures whatever the app throws on mount
```

`scripts/cdp-shot.mjs` takes screenshots of the renderer (optionally hovering an
element first — CSS `:hover` cannot be forced from page JS). `SHOT_WIDTH` /
`SHOT_HEIGHT` control the emulated viewport. The CDP scripts use the global
`fetch`/`WebSocket`, so they want Node ≥ 22.

## Sandboxed client (macOS)

Development never touches the daily Spotify install. The patched client is a
separate bundle (the author keeps it at `/Applications/Spotify Label.app`, with
an inverted icon generated by `scripts/make-icon.py`), and `scripts/start.sh` /
`scripts/stop.sh` swap between the two.

Hard-won facts encoded in those scripts:

- **Spotify enforces a single running instance** regardless of where the bundle
  lives or what its bundle identifier is. The two clients trade places; they
  cannot run side by side.
- **Launch through `open`, never the binary.** Executing the Mach-O directly
  from a shell starts a process that looks alive in `ps` but never creates a
  window.
- **Give the patched bundle its own identifier** (`com.spotify.client.label`).
  While both bundles claimed `com.spotify.client`, LaunchServices resolved by
  identifier and `open -a /Applications/Spotify.app` happily started the copy.
  Sign-in survives the change.
- **Re-sign after touching the bundle.** Editing `Info.plist` or the icon breaks
  the code signature and launchd refuses to spawn the app (RBS error 153,
  "Launch failed"). Fix:
  `codesign --force --deep --sign - "/Applications/Spotify Label.app"`.
- **Do not escape dots in `pkill -f` patterns.** BSD pkill exits 0 while killing
  nothing when given `"Spotify Label\.app"`. Match the plain executable path.

## Traps worth knowing about

- **`Spicetify.ReactComponent` is bigger than its typings.** `Cards`, `Chip` and
  `Dropdown` exist at runtime but are undeclared; access goes through one typed
  shim (`src/types/runtime.ts`). Conversely `TextComponent` *is* declared but
  throws React error #31 on 1.2.94 with any props — plain markup styled from
  `app.scss` is used instead.
- **`searchAlbums` is addressed by a persisted-query SHA-256 hash** that changes
  with Spotify builds. The extension watches the client's own search traffic and
  stores the current hash in `localStorage`; `pathfinder.ts` carries a baked-in
  fallback captured on 1.2.94.583. Nothing to do on update — it heals itself.
- **A page reload is not a restart.** After `location.reload()`,
  `Spicetify.GraphQL` exists while `GraphQL.Request` is still unbound. The
  extension waits for the *method*, not the namespace.
- **Spotify tints its top bar** with the extracted cover colour of the last
  entity page and nothing resets it on custom-app routes — the stray colour
  arrives as an inline `--background-base` on the bar itself, so overriding
  `background-color` with that same variable is a no-op. The extension replaces
  the variable.
- **The album cache is versioned** (`label-catalog:album-cache:v2`). Any change
  to the `AlbumDetail` shape must bump the version, or stale entries from a
  previous build will crash the first render.
- **Local-storage keys** in use: `label-catalog:searchAlbums-hash`,
  `label-catalog:album-cache:v2`.
